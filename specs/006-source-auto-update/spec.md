## User Scenarios & Testing *(mandatory)*

### User Story 1 - 定期检查与无变化判定（Priority: P1）

管理员为已收录 Skill 配置结构化 GitHub 来源后，系统在定时或手动触发时读取同一不可变修订的
完整内容与适用许可，判断是否有内容变化，并记录真实检查时间；无变化不创建提交。

**Why this priority**：可靠检查是自动更新的入口；不能稳定判定无变化，就无法安全地进入替换流程。

**Independent Test**：使用受控 GitHub 来源或注入来源夹具，分别模拟无变化、内容变化、目录截断、
404/403/限流/超时和 pinned/Release 不可用，检查状态、修订、内容摘要、检查时间与副作用。

**Acceptance Scenarios**：

1. **Given** 已启用的 GitHub 分支来源，**When** 执行一次检查，**Then** 系统先解析到不可变提交，
   读取该修订的完整文件树与适用许可，输出 unchanged 或 candidate，并记录真实检查时间。
   对应 FR-008、AC-009。
2. **Given** 上游提交变化但文件内容与当前同步摘要相同，**When** 执行检查，**Then** 结果为 unchanged，
   不创建空内容提交，也不把新提交误报为内容升级。对应 FR-008、AC-009。
3. **Given** 相同内容被重复检查，**When** 再次执行，**Then** 结果幂等，当前内容与提交历史不变。
   对应 FR-008、NFR-004。
4. **Given** 一个来源返回 404、403、限流、超时或目录截断，**When** 批量检查执行，
   **Then** 该来源失败并给出稳定原因，其他来源继续检查，当前版本不被删除或覆盖。
   对应 FR-008、FR-009、AC-010。

### User Story 2 - 单版本完整替换（Priority: P1）

当候选内容通过完整校验后，系统整体替换该 slug 的当前内容：新文件出现、上游删除的文件消失，
slug 与站内元数据保持，公开索引、详情和下载只呈现一个当前版本。

**Why this priority**：只做增量覆盖会留下旧附件和错误版本；完整替换是单版本语义的核心。

**Independent Test**：准备两个受控修订，第二版新增一个文件并删除旧脚本；执行检查与替换后，
逐路径、逐字节核对当前内容、详情、下载包和索引，确认只保留新版且站内标签/备注未丢失。

**Acceptance Scenarios**：

1. **Given** 上游 v2 新增文件并删除 v1 附件，**When** 候选通过校验并应用，
   **Then** slug 不变、列表仍只有一项、当前内容与下载包包含新文件且不含旧附件。
   对应 FR-008、AC-009。
2. **Given** 上游声明版本未变化但主文档或附件内容改变，**When** 执行检查，
   **Then** 系统按内容摘要识别变化并更新，不因版本字符串相同而跳过。对应 FR-008、AC-009。
3. **Given** 上游未声明版本，**When** 内容发生变化，**Then** 仍按来源修订与内容摘要更新，
   不编造 SemVer，也不覆盖站内标签、备注、用法和分类。对应 FR-008、AC-009。
4. **Given** 单文件来源变为目录来源或反向变化，**When** 新候选合法且完整，
   **Then** 按完整新清单替换，旧路径不残留，既有 slug 与分享链接保持。对应 FR-008、AC-009。
5. **Given** 候选包含脚本或 Agent 配置，**When** 检查、校验和替换执行，
   **Then** 这些文件只作为不可信数据保存和分发，不执行、不调用、不安装其依赖。
   对应 FR-007、AC-012。

### User Story 3 - 许可、本地修改与冲突保护（Priority: P1）

当许可缺失或变化、当前内容被本地修改、远端基线变化或候选非法时，系统暂停替换并保留当前版本；
管理员能看到明确状态和原因，由管理员决定恢复跟踪、修正来源或转为手动维护。

**Why this priority**：自动更新不能以“有上游变化”为由覆盖人工修改或无许可内容；失败保留是可信维护的前提。

**Independent Test**：分别注入许可缺失/变化、本地内容修改、并发基线变化、路径越界、符号链接、
子模块和非法候选，确认每种情况都失败关闭、当前版不变、其他来源不受影响。

**Acceptance Scenarios**：

1. **Given** 上游许可缺失或与已记录许可不一致，**When** 执行检查，
   **Then** 该来源进入 policy_blocked，候选不应用，当前内容保留，并报告需要管理员复核。
   对应 FR-008、AC-010。
2. **Given** 当前内容摘要与上次成功同步摘要不一致，**When** 上游出现新候选，
   **Then** 系统返回 conflict，不覆盖本地修改，管理员可选择恢复跟踪或转自维护。
   对应 FR-008、AC-010。
3. **Given** 检查与更新期间远端基线前进或并发运行已提交新内容，**When** 当前运行尝试应用，
   **Then** 运行失败关闭或标记为过期，不 force push、不重写历史、不覆盖新版本。
   对应 FR-008、FR-009、AC-010。
4. **Given** 候选包含截断目录、子模块、符号链接、越界路径或非法元数据，**When** 校验执行，
   **Then** 候选被拒绝，当前版本保留，诊断只报告位置和稳定规则。对应 FR-008、NFR-003、AC-012。
5. **Given** 一个来源失败而其他来源有合法更新，**When** 批次继续，
   **Then** 其他来源仍可检查；若整批构建失败，则不发布该批，旧站保持可用。
   对应 FR-008、FR-009、AC-010。

### User Story 4 - 状态记录、重跑与恢复（Priority: P2）

管理员能查看每个来源最近检查和最近成功更新、来源修订、内容摘要、结果与失败原因；提交、构建和
部署分开显示；部署失败后线上保留旧站，可按同一提交重跑或通过受控历史恢复。

**Why this priority**：自动更新必须可诊断、可重试、可恢复，否则失败会被误报为成功或造成版本回退。

**Independent Test**：模拟无变化、有更新、构建失败、部署失败、并发过期和恢复提交，
检查运行记录、重跑幂等、旧站保留、slug/旧链接稳定与历史未被改写。

**Acceptance Scenarios**：

1. **Given** 一次批量检查完成，**When** 管理员查看运行结果，**Then** 可区分每个来源的
   unchanged、candidate、updated、failed、conflict 或 policy_blocked，以及检查时间与来源修订。
   对应 FR-009、AC-011。
2. **Given** 内容已提交但部署失败，**When** 管理员查看状态，**Then** 明确显示“提交成功、部署失败”，
   线上保持上次正常站点，不报告 published。对应 FR-009、AC-011。
3. **Given** 同一提交需要重跑，**When** 管理员重新发布，**Then** 不新建内容提交，重跑幂等，
   成功后状态变为已发布。对应 FR-009、AC-011。
4. **Given** 需要回到上一份有效内容，**When** 管理员通过受控历史生成恢复提交并重新发布，
   **Then** 既有 slug、旧链接和单版本保持，不强制改写或清除 Git 历史。对应 FR-009、AC-011。
5. **Given** 无变化检查，**When** 管理员查看记录，**Then** 可看到真实检查时间，
   但不会因时间戳制造空提交；公开页面不显示运行日志或内部错误。对应 FR-009、AC-011。

### User Story 5 - 每日调度与运维说明（Priority: P2）

系统按已确认的每日时间执行来源检查，同时提供管理员手动触发；README 说明来源配置、状态查看、
失败处理、许可与冲突、调度时区及恢复方式，未授权触发不产生写入副作用。

**Why this priority**：没有可执行的调度与运维说明，自动更新无法被管理员安全启用和维持。

**Independent Test**：在受控环境验证手动触发与计划触发的同一代码路径、时区配置、开关、失败重跑
和无变化运行；按 README 从干净 checkout 完成一次来源查看、失败处理和恢复演练。

**Acceptance Scenarios**：

1. **Given** 调度已配置，**When** 到达每日 03:17 Asia/Shanghai，**Then** 运行来源检查；
   平台延迟、跳过或停用不承诺准点 SLA，管理员可手动重跑并看到真实运行记录。
   对应 FR-008、FR-009、Q-004。
2. **Given** 某个来源被禁用，**When** 调度或手动检查执行，
   **Then** 不读取或替换该来源，其他启用来源仍可检查。对应 FR-008。
3. **Given** README 的运维章节，**When** 管理员从干净 checkout 按说明操作，
   **Then** 能配置结构化来源、查看状态、处理许可/本地冲突、重跑失败并执行受控恢复，
   示例不含真实凭证。对应 FR-009、AC-011。
4. **Given** 未授权身份尝试触发检查或替换，**When** 请求执行，
   **Then** 不产生仓库、产物或线上副作用，也不回显凭证。对应 FR-007、AC-008。

### Edge Cases

- 上游分支移动、Release 被删除、最新 Release 为草稿/预发布：报告 unavailable 或按策略失败，
  不静默退回分支。
- pinned 修订不可达：检查失败，不自动前移；原固定内容保持。
- 文件树被截断、出现子模块、符号链接、越界路径或不允许的点文件：候选拒绝，当前版保留。
- 上游仓库改为私有、重命名、404、403、429、超时：逐项失败，其他来源继续。
- 许可文件缺失、许可声明变化或适用范围不明确：暂停自动替换并报告，不假定仓库整体授权。
- 当前内容被本地修改、并发运行提交或基线前进：conflict，保留当前内容，不 force push。
- 同内容不同提交、同版本不同内容、无版本声明：分别按 unchanged、内容变化和修订记录处理。
- 上游删除附件、单文件与目录互换、附件路径变化：完整替换并清理旧路径。
- 候选非法、构建失败、部署失败、运行过期：失败关闭，旧站保留，按同一提交重跑。
- 无变化但站点落后当前提交：可显式重发当前快照，不制造空内容提交。
- 调度延迟、跳过或时区配置错误：记录真实运行/失败，不声称准点或已发布。
- 运行摘要、日志、README 和公开页面：不得出现 token、cookie、上游响应正文或内部异常原文。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-008（本轮）**：系统 MUST 为已收录 Skill 保存结构化来源配置，至少包含 provider、
  repository、path、ref_policy（branch/release/pinned）、ref、enabled；首版 MUST 仅支持
  GitHub 公开仓库单文件或 Skill 目录。每个 Skill 的来源状态 MUST 可标识未配置、启用、暂停或不支持；
  非 GitHub 来源 MUST 显示未配置或不支持，不得宣称已自动更新。检查 MUST 先解析到不可变提交，
  再读取同一修订的完整文件树与适用许可；MUST 拒绝截断目录、子模块、符号链接、越界路径和普通
  网页 URL。变更检测 MUST 覆盖
  主文档及全部附件的内容摘要，不能只比较声明版本。无变化 MUST 为 unchanged，不创建内容提交；
  内容变化 MUST 先完整获取并校验候选，再整体替换当前内容并移除上游已删除文件；站内显示名、标签、
  备注、用法、分类及来源配置（除已同步修订/摘要/许可基线/时间）MUST NOT 被同步覆盖。声明版本未变但内容变化 MUST 仍按内容摘要更新；同内容
  不同提交 MUST 只记录检查，不伪造升级。Release 策略 MUST 选择最新非草稿、非预发布 Release；
  不存在时报告 unavailable，不退回分支；pinned 不自动前移。系统 MUST 持久化最近成功同步的许可
  路径与摘要，用于后续缺失/变化检测；许可缺失或变化 MUST 暂停自动替换并报告；本地内容与上次同步摘要不一致或远端基线变化 MUST 返回 conflict 并保留当前内容。单个来源
  失败 MUST NOT 阻止其他来源检查；全量构建失败 MUST 阻止整批发布。**验收**：User Story 1～3；
  AC-009、AC-010、AC-012。
- **FR-009（本轮）**：系统 MUST 记录每次检查/更新的运行标识、触发方式、来源、检查时间、最近成功
  更新、来源修订、内容摘要、逐项结果与稳定错误原因；无变化检查 MUST 记录真实检查时间但不制造空
  提交。内容提交、构建和部署状态 MUST 分开报告；部署失败 MUST 保留上次正常站点，允许按同一提交
  重跑且不重复新建内容提交。需要恢复时 MUST 通过受控历史恢复提交并重新构建发布，保持 slug 和旧
  链接，不强制改写历史。公开页面 MAY 展示该内容最近成功同步时间和来源标识，但 MUST NOT 展示运行
  日志、内部错误或凭证；管理员 MUST 能从运行记录区分来源错误、许可阻断、本地冲突、构建失败和
  部署失败。**验收**：User Story 4～5；AC-010、AC-011。
- **FR-007（本轮）**：自动检查与替换 MUST 仅由受信任的定时任务或管理员/授权 Agent 手动触发；
  未授权触发 MUST 无写入副作用。凭证 MUST 由受信任环境提供，不进入来源配置、页面、产物、日志或
  运行摘要。上游 Skill 的正文、脚本和配置 MUST 作为不可信数据处理，MUST NOT 执行其脚本、测试或
  安装依赖；合法原件仍按字节保存和分发。**验收**：User Story 5；AC-008、AC-012。

### Key Entities

- **来源配置（SourceTracking）**：provider、repository、path、ref_policy、ref、enabled，
  以及最近同步修订、内容摘要和最近同步时间；与站内展示元数据分离。
- **维护运行（MaintenanceRun）**：运行标识、触发方式、开始/结束时间、逐来源检查结果、
  提交/构建/部署状态和稳定错误原因；用于管理员查看与重跑，不公开展示内部日志。
- **候选快照（CandidateSnapshot）**：同一不可变修订的主文档、附件、许可、路径清单和内容摘要；
  只有完整验证后才允许替换。
- **内容记录（ContentRecord）**：slug、显示信息、标签、备注、用法、来源配置与内容路径；
  同步不得覆盖站内字段。
- **发布结果（PublicationOutcome）**：内容状态、部署状态、提交标识、运行链接、公开链接和错误码；
  内容提交、构建和部署不得合并成单一“成功”。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **US006-SC-01**：100% 的来源检查先解析到不可变修订；截断目录、子模块、符号链接、越界路径和
  普通网页 URL 的接受次数为 0。
- **US006-SC-02**：上游新增/删除附件后，100% 的更新保持同一 slug 且列表只有一个当前版本；
  旧路径删除率 100%，站内标签、备注和用法保留率 100%。
- **US006-SC-03**：相同内容重复检查 100% 返回 unchanged，不新增内容提交；声明版本未变但内容
  变化时 100% 能按内容摘要更新。
- **US006-SC-04**：404/403/限流/超时/非法候选/许可变化/本地修改/并发冲突 100% 失败关闭，
  当前版本保留；单个来源失败不阻止其他来源检查；整批构建失败时发布次数为 0。
- **US006-SC-05**：部署失败 100% 保留上次正常站点，并按同一提交重跑时不新增内容提交；

- **US006-SC-06**：运行记录 100% 区分检查、内容更新、提交、构建和部署；凭证与上游响应正文在
  输出、日志、README 和公开页面中的回显次数为 0；上游脚本执行次数为 0。
- **US006-SC-07**：每日 03:17 Asia/Shanghai 的检查配置和手动重跑使用同一代码路径；平台延迟或
  跳过时不误报准点或已发布。
